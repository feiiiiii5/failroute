## Silent failure-routing in red-teaming metrics: degraded/failed judges can still produce "results"

While auditing exception-handling in LLM red-teaming tooling I found two
related patterns in deepteam's metric layer. Both can cause a metric to
report on a degraded or failed judge without surfacing any error.

(These are correctness observations, not security issues — filing publicly.)

### 1. Bare-except during metric initialization silently degrades the judge's system prompt

In metric `__init__` (e.g. `deepteam/metrics/bias/bias.py:46-49` at v1.0.9,
and the same shape across roughly 40 metric classes under
`deepteam/metrics/`):

```python
try:
    self.system_prompt = model.get_system_prompt()
except:
    self.system_prompt = ""
```

If a custom or misconfigured `DeepEvalBaseLLM` does not support
`get_system_prompt()` (or raises for another reason), initialization silently
degrades to an empty system prompt. All subsequent scoring then runs under a
judge that was never set up as intended, and nothing in the logs marks the
degradation. Because the bare `except:` also catches `KeyboardInterrupt` and
`SystemExit`, even interrupted initializations leave the metric in this
degraded state.

Suggested direction: narrow to `except AttributeError` for the
capability-probe case (and log a warning once); let other exceptions
propagate.

### 2. `is_successful()` contains a comparison that can never raise, masking scoring failures

In the RT metrics' `is_successful()` (e.g.
`deepteam/metrics/hallucination/hallucination.py:225-228` at v1.0.9):

```python
try:
    self.score == 1
except:
    self.success = False
return self.success
```

The comparison `self.score == 1` cannot raise (including when `self.score`
is `None`), so the `except` branch is unreachable. When scoring never
produced a valid score, the method returns whatever `self.success` held from
a previous run — a failed evaluation can therefore be reported as successful,
silently flipping red-team conclusions.

Suggested direction: `self.score is not None and self.score == 1` (or route
through `self.error`).

### Minimal reproduction of the interaction

```python
class M:
    score = None
    success = True          # stale value from an earlier run

    def is_successful(self):
        try:
            self.score == 1     # None == 1 -> False; never raises
        except:
            self.success = False
        return self.success

print(M().is_successful())      # True — a failed evaluation reports success
```

### How this was found

I build a small AST-based detector for this defect family ("failure-routing":
a failure converted into a success-looking outcome at the wrong layer). It
surfaced these patterns mechanically; everything above was then verified by
hand against v1.0.9 before filing. Happy to draft a PR for either fix if the
direction looks right to the maintainers.
